# APPEND限定更新 v1：仕様案（2026-11-23）

状態: **設計案／未実装**。本ファイルの追加は実装承認、GAS SYNC、本番Web App再デプロイ、保存データ更新を意味しない。

## 目的と非目的

現行の「同一企業＋同一応募月＋同一人物」を1件とする厳格な重複判定は維持し、APPENDで次の2つだけを安全に扱う。

1. 同じ応募の `対応状況` が変わったときに更新する。
2. 以前は求人CSV未突合だった応募を、後から実際にJOINできた求人CSVで補完する。

「新CSVを全面的に正とする」、同一人物の別求人への代表切替、選考ステータスの順位判定、応募イベント全件保存、ステータス履歴CSVの必須化、過去応募当時の求人条件の完全復元は対象外。

既存の CREATE / REPLACE / AGG_DAILY の意味、PERSON_ID / PERSON_NAME / I1キー、schema 3.0、requestId再送防止、DataStore stage→verify→commit、JOB/APP ID、共有Viewerを不用意に変更しない。

## 1. 現行処理の根拠

- `index.html`: CSV取込後、JOIN前の `seenKeys` で人物×月の先頭行を残す。JOIN後 `vaaApplyApplicationIdentities` でI1識別キーの再重複除外をする。現在のアップロード内同人物の後続行は保存まで届かない。
- `append-identity-v1.js`: PERSON_ID/PERSON_NAMEのI1キーは企業ID＋応募年月＋応募者ID/氏名からHMAC生成。仕事番号・応募日時は含まない。
- `index.html` `buildNormalizedSheetsModel`: `applicationData` と `jobAnalysisMaster` に正規化。応募行には `仕事番号`、`応募日時`、`対応状況`、`求人参照ID`、`求人データ突合フラグ` がある。求人マスタの `求人分析情報ソース` は `JOB_CSV` / `APPLICATION_EMBEDDED`。
- `central-api/11_Append_Merge.gs`: APPENDで同じ応募識別キーがあれば `skippedAsExisting` として除外し、既存応募・既存求人マスタは上書きしない。
- `analysis-core.js`: 保存済み `求人データ突合フラグ` と求人参照IDから実際のmatched集計を決定。フラグの意味を勝手に変更しない。
- APPENDでは現状、応募CSVのアップロードが必要。求人CSV単独アップロードのみで既存DataStoreを補完する機能は、本設計には含まない。

## 2. 人物と応募の照合

**人物の既存判定を変更しない**: 保存済みとアップロードが同じ非空I1識別キーなら「同一人物・同一月」。異なれば新規応募（現行どおり）。

この人物の `対応状況` 更新はさらに条件を絞る:

- 人物識別方式がPERSON_IDまたはPERSON_NAME、I1キー完全一致。
- 企業ID一致。
- 仕事番号は既存と入力の **正規化後** が一致。タイトル文字列を使わない。空欄・不正キーなら更新禁止。
- 応募日時が日付＋時刻（秒精度に正規化）で一致。日時不明・日付しかない場合は安全側で自動更新しない（検証対象）。
- `対応状況` は入力側に非空値がある場合のみ、保存済み値と異なれば更新。状態の前後順位は判断しない。
- 仕事番号または応募日時が異なる場合、その人物の代表応募は維持し、ステータス更新も実行しない。
- 応募日時・仕事番号・応募媒体・属性・識別キー・レコードIDは、ステータス変更に便乗して書き換えない。
- 更新日時のCSV列は現状ない。**後からアップロードしたCSVが情報として新しいという運用上の前提** を置く。古いCSVの再投入によるステータス逆戻りは自動判別できない。

同じCSV入力中に **完全に同じ人物・求人・応募日時** のステータスが複数あり、値が競合する場合、行順から新旧を推定して更新するべきではない。初版の受入テストで停止/更新スキップ/警告の扱いを確定させる。保守的な推奨は当該ステータス更新スキップ＋件数表示。

## 3. 求人CSV補完

**求人の同一性**: 企業ID＋正規化仕事番号。 `JOB_CSV` があったということ自体は応募イベントの同一性を保証しない。

| 保存済み | 今回JOIN | 求人マスタの方針 | 応募行の方針 |
|---|---|---|---|
| 該当求人キーがマスタに存在しない | 同一求人キーのJOB_CSVにJOIN成功 | 新規JOB作成 | 該当する保存済み応募を既存APP IDのまま紐づけ、突合フラグを1へ |
| APPLICATION_EMBEDDED | 同一求人キーのJOB_CSVにJOIN成功 | 既存JOB IDを維持してJOB_CSVへ昇格、求人CSV由来の有効値を格納 | 該当する保存済み応募について突合確認できればフラグを1へ |
| JOB_CSV | 同一求人キーのJOB_CSVにJOIN成功 | 既存求人属性を維持。給与改定などによる上書きをしない | 既存で突合済みなら維持、未突合だった対象応募はJOIN成功時のみ1へ |
| 既存JOB_CSV | 今回求人CSVなし | 変更なし | 突合フラグを1→0に戻さない |
| 既存求人A | 今回の別求人B | AからBへ給与・職種等を流用しない | 代表応募の仕事番号・求人参照IDをBへ無条件に切替えない |

- `求人データ突合フラグ` を 0→1 にするのは、その対象応募が今回アップロード内で **本当に同じ求人キーの求人CSVとJOINした** と証明できる場合のみ。既存のJOB_CSVマスタにリンクしただけで1にしない。
- 既存の同一求人キーのJOB_CSVは原則固定。「求人CSVの給与が変更されたら過去応募の給与が遡及して変わる」を避ける。
- `APPLICATION_EMBEDDED` → `JOB_CSV` 昇格は同じ求人キーを参照する複数応募の求人属性にも影響する。昇格件数、属性変化をテスト・統計に含める。
- `JOB_CSV`由来の項目のうち未取得・空欄がある場合の個別補完は初版では対象外。給与修正などの正式な訂正はREPLACEの利用を案内する。
- 仕事番号が異なる別求人の情報で保存済み代表応募を埋めない。

## 5. 現行JOIN前の先頭行重複排除による重要制約

現在のブラウザは「同一人物＋企業＋月」の最初の応募行だけを残し、後続行をJOIN前に破棄している。
保存済みの代表がJ101・11/05で、今回CSVに同人物のJ202・11/18が先に載り、J101・11/05の更新状態が後に載る場合、**J101の正しい更新が保存APIまで届かない**。

これを無視して「同一応募は常に更新可能」と表示してはならない。

まず最小実装では現行のCSV先頭行採用を維持し、上記を「更新スキップ可能な既知制約」としてテスト・計測する。実運用で頻出するなら、**ブラウザ内だけ一時的に全候補を保持し、個人識別キー＋同求人＋同日時でGAS側が厳密照合できるよう、最小限の更新候補を送る**拡張を別工程にする。生氏名・応募者IDは保存・送信せずHMACキーだけを利用する。全応募イベントの永続保存は不要。

※これは誤上書きを回避する「安全側に取りこぼす」設計。取込時の代表応募選択自体を変える提案ではない。

## 6. 実装境界・統計

想定変更箇所:
- `central-api/11_Append_Merge.gs`: 既存I1応募キー一致時に限定項目更新を判定、既存APP ID保持。AGG_DAILY経路は現行維持。
- `central-api/12_Append_DataStore.gs`: 現行stage/verify/commitの規約を変更せず、統合結果と更新統計を引継ぐ。
- `central-api/13_Append_Update_Guard.gs`: 結果の集計フィールドを必要に応じて拡張。互換性チェックは保持。
- `index.html`: CSV前処理で更新候補が失われる制約を検証。初版では重複判定自体は変更しない方針。表示は結果件数の最小追加にとどめる。
- `tests/append-merge-core.test.cjs` 等: 追加/更新/求人補完/誤更新阻止/再送/旧マスタ互換性/ビューア集計を回帰テスト。

候補統計: `addedApplications`、`statusUpdatedApplications`、`jobPromotedToCsv`、`jobAddedForExistingApplications`、`applicationsNewlyMatchedToJobCsv`、`unchangedDuplicateApplications`、`statusUpdateSkippedDifferentEvent`、`statusUpdateSkippedAmbiguous`。大きな新規UIや設定画面は不要。

特に `求人データ突合フラグ` が0→1になれば、`analysis-core.js` の「求人CSV突合済み」集計が変化する。求人マスタのみ昇格しフラグ0のままの別応募についても既存の定義を維持する。

## 7. 安全な実装順序

1. まず「純粋統合ロジック」だけを隔離環境で実装し、A01〜A18テストを固定。
2. 正規化/求人マスタ対応、欠落列、旧ソース属性をテストし、全既存回帰テストを実行。
3. 必要ならプロトコル・統計の互換性確認。既存GASの requestId V2/READY/RETIRED 安全性を維持。
4. 実データなしの隔離Web App / QA用Sheetsで CREATE、APPEND、REPLACE、AirWork などを検証。
5. 本番ソースSYNCとWeb App新バージョンデプロイは **別途明示的な承認と安全確認後**。GitHubへの設計書・コード変更だけでは本番反映とみなさない。

## 8. 仕様確定前の確認ポイント（少数）

- **更新CSVの鮮度**: 元CSVにステータス更新日時がないため「アップロード順を更新順とみなす」運用でよいか。古いCSV再投入による逆戻りは検知できない。
- **同じCSV内の同一イベント競合**: 行順で勝手に選ばず、当該ステータス更新をスキップして警告する案を推奨。
- **日付のみのCSV**: 応募日時が日付だけの場合、同一応募を厳密照合できないので対応状況を自動変更しない案を推奨。
- **取りこぼし**: 先頭行以外に本当の更新対象がある場合を初版で取り込むか。初版は安全優先でスキップし、必要性を計測する案を推奨。

以上は独立した**仕様検討文書**であり、現行APPENDの動作や本番データは変更していない。
