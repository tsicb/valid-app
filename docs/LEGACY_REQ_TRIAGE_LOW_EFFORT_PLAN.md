# 旧REQ履歴103件の低工数整理方針（設計のみ）

更新: 2026-11-22 / Status: **DESIGN ONLY — GAS未改修・未SYNC・本番データ未変更**

## 目的と現状

旧READY 41件の両アーカイブCOPY・個別READY replay確認・Script PropertiesからのRETIREは完了。独立監査 `pass:true`、移管モードOFF。容量監査は **262,551 / 512,000 bytes (51.3%)**、`REQ_` 104件（READY100・ERROR4）。現段階で緊急削除は不要。

残る104件のうち、**103件**は旧履歴整理の対象候補で、以下の監査区分（重複加算しない）に分かれる。

| 現行監査区分 | 件数 | ソース上の正確な意味 | 未確認事項 |
|---|---:|---|---|
| `quarantinedLegacyReady` | 39 | 旧UPDATE READY。更新方式とpayload digestがなく、V1再利用の同一性を証明できない | 参照先が現存管理フォルダ内か、ゴミ箱・削除済みか |
| `quarantinedTargetReady` → `targetCannotOpen` | 46 | DriveApp.getFileById が失敗（原因不明） | 管理フォルダの完全列挙から存在を確認できるか |
| `quarantinedTargetReady` → `targetTrashed` | 14 | Drive上の参照先ファイルがゴミ箱にある | 現在運用対象から外してよいか |
| `nonReady` | 4 | ERROR等のREADYではない履歴（容量監査上はERROR4） | 処理副作用の有無、再試行・復旧予定 |
| V2 READY除外 | 1 | V2ジャーナル管理下。上の103件と別 | 今回扱わない |

注: 39・46・14・4は**監査の分類として互いに独立**。ただし旧UPDATE39件の参照先状態を未調査のため、その中に実質的な「ゴミ箱／不明対象」のシートが含まれる可能性はある。従って「93件が消失」等と断定しない。

## 原則（業務保管方針）

- **現役の個社管理シートが共通管理フォルダまたは直下1階層のサブフォルダに現存するか**を一次判断材料とする。単なる `getFileById` 失敗だけでは「消えた」と言わない。
- 個社管理シート以外に、当該Spreadsheet IDが `RPTREG_` レジストリや `VIEWER_` 共有マッピングから参照されている可能性も保護する。レジストリ自体が古い場合もあるため「参照あり」は即現役と断定せず、**要確認**に留める。
- 個社シート・関連JSONは分析データの本体だが、`REQ_` は **requestIdの再送・重複実行防止・処理途中の復旧**の役割を持つ。同じIDを新規として再受付しない対策を実装しない限り、REQだけの単純削除は認めない。
- **現行のV1（正常READYの再利用）とV2（予約／結果ジャーナル）には、無効な旧UPDATEやERRORをREADYとして混入させない**。隔離が必要になった場合は通常台帳と別の名前空間／タブ。
- 「不明だから永久保管」も「開けないから一括削除」も採用しない。ユーザーが不要とした廃棄済みデータは、再送安全性を別途担保できれば履歴詳細を退役させられる。
- 保管期間・廃棄方針は、**保管フォルダ外かつ有効な外部参照なし**であること、ERRORの副作用なし等を検証した後で決定する。永久保存を前提にしない。

## 最小工数の実装順（提案、未着手）

### Phase A: 1回実行の集計監査（最優先）

既存の `central-api/25_Request_Ledger_V2_Legacy_Batch_Migration.gs` に **管理者専用の読み取り専用関数を1個**追加する方針。追加のCSVアップロード・スプシ作成・手動1件ずつの確認は不要。

想定関数名: `vaaLedgerProdResidualReqTriageReadOnly`（未実装）。

入力は既存のScript Propertiesと既存Drive管理フォルダ、既存レジストリ／Viewerマッピング。実行時に以下を行う：

1. Script Propertiesの全スナップショットから `REQ_` を読み、`39+46+14+4` の分類を独立に再構築。V2 READYを分離。記録本体・IDは出力しない。
2. `API_CONFIG.SHEET_OUTPUT_FOLDER_ID` の直下と、その直下の第1階層サブフォルダを **すべて**列挙し、ファイルIDの集合を作る。フォルダがゴミ箱にある／アクセス失敗／列挙中断／上限超過なら監査を不合格（`inventoryComplete:false`）とし、非掲載を「削除済み」とは認定しない。既存 `syncReportRegistryFromFolder_` は **書き込み処理かつ500件上限**なので監査には流用しない。
3. 旧UPDATE39件、参照先不明46件、ゴミ箱14件、ERROR4件の参照先を、完全列挙した集合と照合。存在・非存在・記録内のID未設定・分類不能を区別する。1つのシートが複数REQに紐づく可能性があるため、REQ件数とユニークなシート数は別集計。
4. `RPTREG_` / `VIEWER_` のSpreadsheet IDとの一致（あれば要確認）と、REQレコードのステータス／進行中leaseの有無を集計。既存の関連情報は**読み取りのみ**で使い、変更しない。JSONが不正・読み取り不能なら安易に非参照とみなさない。
5. `getProperties()` の実行前後の完全一致を検証して `sourceStable:true` とし、ログにはカテゴリーごとの件数・推定byte数・`inventoryComplete`・`errorCode`・各write/delete 0だけを出す。requestId、IDハッシュ、Spreadsheet URL、顧客名、元JSON、機密値は一切ログに出さない。

想定出力区分：
- **CURRENT_MANAGED**: 現在の管理フォルダ内にあり、保管必要性あり（自動削除候補外）
- **OUTSIDE_WITH_LINK**: フォルダ外だがRegistry/Viewerに参照あり（整合性の個別確認）
- **OUTSIDE_NO_LINK**: フォルダ外、参照なし（整理有力候補。ただし再送対策前の削除禁止）
- **TRASHED**: ゴミ箱内の履歴（整理有力候補。ただし再送対策前の削除禁止）
- **ERROR_REVIEW**: ERROR等の未完了履歴（副作用を確認するまで削除禁止）
- **UNKNOWN**: 列挙失敗・データ不正等（自動削除候補に含めない）

監査関数自体は **`propertyWrites:0, propertyDeletes:0, archiveWrites:0, requestPosts:0`**、GASエディタから最大1回の手動実行で完結させる。GitHubでコードと回帰テスト／SHA manifestを検証後に、**別途承認してGASへSYNC** する。エディタからの一度の読み取り専用実行は `doPost` のWebアプリ再デプロイ不要の見込み。

### Phase B: 監査結果を見て「何もしない／最小隔離」の二択

- 現状容量51.3%で、そもそも急いで処理しなくても安全なら **作業しない**。無理に103件全部整理しない。
- 整理対象が十分多い場合だけ、既存の**独立非公開バックアップ用スプレッドシート**に通常READYとは別の隔離タブを使う案を検討する（新しいスプレッドシートは原則作らない）。元REQ全文を保存して読み戻し、復旧可能性を証明する。
- **隔離タブを作るだけではREQ削除は不可**。V2予約より前に、隔離したrequestIdを拒否する最小の再送禁止ガード（小型のハッシュ集合等）を設計し、再送・既存READY・ERROR・同時実行・失敗時停止のテストを通す。既存V1/V2の正常READY判定は変更しない。
- 完全一致COPY → ガード有効化/読み戻し → ロック下で段階的にREQ退避 → 独立監査、の順でのみ実際の削除を検討。1件ずつユーザーが実行する負担は避け、監査後に自動バッチを設計する。ただし不明応答からの自動再試行は禁止。
- 追加の保管庫、常時のDrive検索、毎回のシート全件走査、毎回の新規Webアプリデプロイなど、持続的な運用コストを上げる設計はできるだけ避ける。

## 実装前に避けたい誤り

- `getFileById` が46件失敗した事実だけで「46件すべて削除済み」と判断しない。
- 39件の旧UPDATEを正常READYと偽ってV1/V2に混ぜない。
- `syncReportRegistryFromFolder_` を監査として呼ばない（レジストリを更新する）。
- 管理フォルダを直下のみとみなさない（1階層サブフォルダあり）。
- 管理フォルダ列挙が未完了なのに、一覧にないことを根拠に削除候補扱いしない。
- `REQ_` だけ削除して、同じrequestIdのCREATE/UPDATEが再び処理される危険を作らない。
- `RPTREG_` / `VIEWER_` の残存自体をただちに現役シートの証拠とみなさない（古いマッピングの可能性）。
- 103件を「要削除件数」と見なさない。監査区分は業務上の保存必要性の判定ではない。
